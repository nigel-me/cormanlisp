# 09. CI (GitHub Actions)

Workflows live in `.github/workflows/`, helper scripts in `.github/scripts/`.

## What runs

| Workflow | Trigger | Runner | Checks | Status |
|---|---|---|---|---|
| `tools-check.yml` | every pull request, pushes to `master`/`main` | Linux | Lisp files are structurally balanced (`lispcheck.py`, excluding `test/bugs.lisp` and the truncated sql-odbc doc); the test harness and `results.py` work end to end using SBCL as a stand-in Lisp; the `test/agent-eval` tasks are valid | **Verified**: every command was run locally as written; `actionlint` is clean |
| `windows.yml` | manual (`workflow_dispatch`) | `windows-2022` | `release-test`: run the harness against a released Corman Lisp build. `build`: build the kernel and console from source, rebuild `CormanLisp.img`, run the harness | **Unverified**: never run. The YAML passes `actionlint`; the PowerShell scripts could not be run where they were written |

`tools-check.yml` does not test Corman Lisp. It protects the tooling around it.

## Running the Windows workflow

GitHub: Actions tab, "Windows build and test", Run workflow. Options: run the release test, use a specific release asset URL
(otherwise the latest release of `sharplispers/cormanlisp`; a `.zip` or `.msi`), run the build, and the MSBuild toolset (default `v143`).

Each job writes a summary on the run page (totals per test file, failing tests, and a comparison with the baseline if there is one) and
uploads artifacts: `results-release`, `build-logs-and-results` (results, MSBuild text and binary logs, makeimg logs, console logs),
and `corman-build` (the built `clconsole.exe`, `CormanLispServer.dll`, `CormanLisp.img`, kept 7 days).

## What "pass" means

Failing Corman Lisp tests do **not** fail a job: many HyperSpec examples fail on Corman by design. A job fails when

- the run does not finish (crash, hang past the timeout, no results file, damaged file), exit code 1 from `.github/scripts/run-harness.ps1`; or
- a baseline exists in `test/baselines/` and tests that passed there fail now, exit code 2. See `test/baselines/README.md`.

Until baselines are committed, a green job only means the harness ran to completion.

## The two jobs in more detail

- **release-test.** `fetch-release.ps1` downloads and unpacks the release and finds `clconsole.exe`. `run-harness.ps1` writes a
  small wrapper file that loads `test/harness.lisp` from this checkout and calls `run-all` with `:trace-tests t :exit t`, starts
  `clconsole.exe -execute <wrapper>` with empty stdin, waits until the results file has its summary record (then gives the console 15
  seconds to exit before stopping it), and runs `results.py check`, `summary` and, if a baseline exists, `diff`.
- **build.** `msbuild src_vc15.sln` with `PlatformToolset` and `WindowsTargetPlatformVersion` overridden on the command line (the
  projects say `v140_xp` and SDK 8.1, neither installed on a runner), building `zlib`, `CormanLispServer` and `clconsole` only. The IDE
  (MFC), `dlltemplate`, `clboot*` and the installer are not built. Then `makeimg.bat`, then the same harness step against the repository root.

## What is likely to need fixing on the first run

1. **The release asset**: the workflow guesses at the release's file names (`*.zip`, then `*.msi`). If none match, the job lists the assets and
   fails; rerun with `release_url`.
2. **The console not exiting or waiting on stdin**: handled by the timeout and the "results complete" check, but the console's behaviour with
   redirected input is unknown. The console logs are in the artifacts.
3. **The harness's own Corman assumptions** (listed in `08-test-harness.md`).
4. **Building with Visual Studio 2022**: the kernel was written for the 2015 compiler and has MSVC-specific assembly and exception handling
   (see `05-kernel-and-runtime.md`). Compile errors, or a build that compiles and then misbehaves, are both possible. That outcome is itself the
   answer to the toolchain question; keep the `build.log`/`build.binlog` artifacts.
5. **MFC or SDK components** are not needed for the targets built, but a `mt.exe` (manifest tool) lookup failure in the post-build step is possible.

## Making it a gate

1. Run both jobs; fix what breaks (release-test first).
2. Download a run you accept and commit its results as a baseline (`test/baselines/README.md`).
3. Add `pull_request:` to `windows.yml` (probably with a `paths:` filter for `Sys/**`, `CormanLispServer/**`, `Modules/**`, `test/**`).
4. Consider pinning the actions to commit SHAs (they use major-version tags now) and, if the repository is private, watching Windows runner minutes.
